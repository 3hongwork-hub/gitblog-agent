# 루프 엔지니어링 (Loop Engineering) 요약본
> **원작 참고:** "Loop Engineering: Stop Asking Me What It Is" (2026년 6월판, 저자: 화슈/花叔)

---

## 1부. 루프 엔지니어링이란 무엇인가?

### §01 개념의 핵심
* **핵심 명제:** 일을 더 잘하는 방법을 배우는 것이 아니라, **"당신이 일하는 포지션 자체에서 완전히 빠지는 것"**입니다.
* **한 줄 정의 (Addy Osmani):** "루프 엔지니어링이란 에이전트에게 프롬프트를 치는 '사람'의 역할을 '스스로 작동하는 시스템'으로 대체하는 것이다."
* **포지션의 이동:** 기존에는 키보드 앞에 앉아 에이전트를 한 줄씩 지시했다면, 이제는 에이전트를 자동으로 구동하고 결과물을 다시 피드백하는 **'엔진(루프)을 설계하는 사람'**이 되는 것입니다.

### §02 기술 스택의 4가지 레이어
루프 엔지니어링은 기존 기술을 대체하는 것이 아니라, 차곡차곡 쌓아 올린 최상위 층입니다.
1. **프롬프트 엔지니어링 (Prompt):** 단일 문장 케어 ("모델에게 무슨 말을 할 것인가?")
2. **컨텍스트 엔지니어링 (Context):** 컨텍스트 창 케어 ("지금 창에 무엇을 집어넣어야 모델이 문제를 풀까?")
3. **하네스 엔지니어링 (Harness):** 단일 실행(Run) 케어 ("에이전트에게 어떤 도구와 권한을 쥐어줄 것인가?")
4. **루프 엔지니어링 (Loop):** 하네스 위에서 스케줄링 케어 (**"사람 없이 이 과정을 어떻게 무한 반복시킬 것인가?"**)

---

## 2부. 루프는 어떻게 회전하는가?

### §03 하나의 루프를 돌리는 5가지 동작 (Five Moves)
구글 크롬 팀의 Addy Osmani가 구축한 '아침 트리아제(이슈 분류) 루프'를 기준으로 본 5대 동작입니다.
* **Move 1. 발견 (Discovery):** 에이전트가 타이머에 의해 깨어나 시스템 오류, 이슈, 커밋 등을 스스로 스캔하여 '오늘 할 일'을 찾아냅니다. 사람이 일감을 던져주는 것이 아닙니다.
* **Move 2. 핸드오프 (Handoff):** 일을 할 하위 에이전트에게 태스크를 떼어줍니다. 이때 파일 충돌을 막기 위해 독립된 공간(Git Worktree)을 분리하여 제공합니다.
* **Move 3. 검증 (Verification):** **루프에서 가장 중요한 단계입니다**. 코드를 짠 에이전트가 아닌, **다른 프롬프트/모델을 가진 독립된 검증 에이전트**가 "No"라고 말할 수 있는 게이트 역할을 합니다.
* **Move 4. 영속성 (Persistence):** 컨텍스트가 초기화되어도 기억을 잃지 않도록 결과물과 상태(State)를 디스크(Markdown, 티켓 시스템 등)에 기록합니다.
* **Move 5. 스케줄링 (Scheduling):** 이 모든 과정이 내일 아침에도 사람의 클릭 없이 자동으로 다시 실행되도록 타이머를 겁니다.

### §04 루프를 만드는 6가지 구성 요소
1. **자동화 (Automations):** 루프를 스스로 움직이게 하는 엔진 (크론 스케줄러 등).
2. **워크트리 (Worktrees):** 여러 에이전트가 동시에 실행될 때 파일 쓰기 충돌을 방지하는 격리 공간.
3. **스킬 (Skills):** 프로젝트의 규칙과 지식을 `SKILL.md` 같은 고정 파일로 만들어 에이전트가 매번 컨텍스트를 새로 학습하는 비용('의도 부채')을 줄여줌.
4. **커넥터 (Connectors):** MCP(Model Context Protocol) 기반으로 외부 툴(Jira, Slack, DB)과 루프를 연결하여 에이전트의 시야를 확장함.
5. **하위 에이전트 (Sub-agents):** 생성자(Generator)와 판사(Judge)를 철저히 분리하여 상호 감시하게 만듦.
6. **메모리 (Memory):** 대화창이 꺼져도 유지되는 디스크 상의 persistent state 파일.

### §05 메이커-체커 원칙: AI는 자기 코드를 스스로 채점할 수 없다
* **자아도취의 한계:** 에이전트에게 자신이 짠 코드를 평가하라고 하면, 평범하거나 결함이 있는 코드도 자신 있게 훌륭하다고 칭찬합니다. 코드를 짤 때의 '자기 설득 과정'이 컨텍스트에 남아있기 때문입니다.
* **해결책:** GAN(생성적 적대 신경망) 구조처럼 **만드는 놈(Maker)**과 **잡아내는 놈(Checker)**을 구조적으로 분리해야 합니다. 검증하는 에이전트는 무조건 "이 코드는 증명되기 전까지는 부서진 상태다"라는 회의적인 스탠스를 취해야 루프가 정상 작동합니다.

## 3부. 어디서 실행되고 무엇을 지불해야 하는가?

### §06 실제 구동 중인 대규모 루프 사례
* **Stripe의 Minions 시스템:** 일주일에 사람 손을 거치지 않고 **1,300개 이상의 PR을 머지**하는 대규모 엔터프라이즈 루프입니다.
* **성공 비결:** LLM에게 컨텍스트를 알아서 찾으라고 넘기지 않습니다. LLM이 켜지기 전, 결정적(Deterministic)으로 코딩된 오케스트레이터가 Jira, 소스코드 그래프, 문서 등 필요한 재료를 완벽하게 밥상으로 차려놓고 LLM은 오직 '창의적인 코드 작성'만 하게 만듭니다. 규칙으로 해결할 수 있는 영역은 절대 확률형 모델(LLM)에 맡기지 않는 것이 핵심입니다.

### §07 자율 루프의 4가지 숨겨진 비용 (The Costs)
> *"비동기로 홀로 돌아가는 루프는, 홀로 조용히 오류를 쌓아 나간다."* - Addy Osmani

1. **검증 부채 (Verification Debt):** 밤새 테스트를 통과하고 코드 수십 개를 고쳐놨지만, 테스트 코드가 잡지 못하는 실제 결함들이 수면 아래 쌓여 한 번에 터질 수 있습니다.
2. **이해력 부패 (Comprehension Rot):** AI가 내 프로젝트 코드를 매일 대신 짜주기 때문에, 코드는 늘어나지만 내 머릿속의 프로젝트 맵은 몇 달 전에 멈춰버립니다.
3. **인지적 항복 (Cognitive Surrender):** 루프가 너무 잘 돌아가면 인간은 의견을 갖기를 중단하고 AI가 주는 대로 "머지" 버튼만 누르게 됩니다.
4. **토큰 폭발 (Token Blowout):** 에이전트가 루프 안에서 버그에 걸려 밤새 혼자 헛돌며 무한 재시도를 하면 토큰 비용이 급증할 수 있으므로 하드캡 보틀넥(회당 예산, 일일 한도)을 반드시 설정해야 합니다.

## 4부. 어떻게 시작할 것인가?

### §08 도구의 노예가 아닌 엔지니어로 남는 법
* **증폭기로서의 루프:** 루프는 중립적인 '곱하기(×) 기호'와 같습니다. 게으름을 가지고 접근하면 게으름을 대량 생산하고, 이해력을 가지고 접근하면 생산성을 극대화합니다.
* **희소성의 이동:** AI로 인한 '생성(Generation)'의 가치는 제로에 수렴하며, 끝까지 희소하게 남는 것은 **"어떤 코드가 진짜 옳은지 결정하는 인간의 판단력(Judgment)"**입니다.
